Windows神秘卡顿排查 DoSvc的WMI死循环

Windows神秘卡顿排查-DoSvc的WMI死循环

2026年7月04日17分钟阅读

一场”光标夺舍”事故:揪出 Windows DoSvc 的 WMI 死循环

笔记本突然卡到鼠标和光标打架、键盘迟钝得像泡在水里,但前台程序居然还在正常跑。第一时间怀疑自己中了银狐木马。最后发现是 Windows 自带的”传递优化”服务陷入了 WMI 查询死循环——今天这篇是一次完整的复盘,也是一份 Windows 输入卡顿的排查 SOP。

1. 事故现场

2026/07/04 晚上,我在 WSL 里 coding 一个 Wails 程序,大概连续调试了一个小时。然后机器突然开始抽风:

  • 光标和鼠标”打架”:鼠标移动方向和光标实际表现不一致,光标会自己跳、自己飘
  • 键盘输入严重迟钝:敲下去到屏幕出现有可感知的延迟
  • 但前台程序仍然正常运行:VSCode、浏览器都没卡死,功能该响应还是响应
  • 任务管理器自己挂了

这种症状组合太诡异了。前台程序正常说明 CPU/磁盘其实没被打满,被卡住的只有输入子系统。第一反应是——**是不是被 RAT(远控木马)夺舍了? **甚至一度怀疑是银狐家族,毕竟那玩意就是冲着中文用户来的。

事后证明,全错了。这篇就是这个错误直觉是怎么被一步步用日志打脸的过程。

2. 排查方法论:SRE 分层排除法

事后回看,这次能用 1 小时内锁定根因,靠的不是经验,是一套固定的分层排除逻辑。把它写下来当作以后所有 Windows 神秘卡顿的 SOP:

┌─────────────────────────────────────────┐
│  L0  资源快照:CPU / 内存 / 磁盘 / 网络  │ ← 看是不是单纯资源耗尽
├─────────────────────────────────────────┤
│  L1  进程画像:谁在吃?签名是否合法?      │ ← 找嫌疑犯
├─────────────────────────────────────────┤
│  L2  持久化+网络:启动项/计划任务/外联   │ ← 排除恶意软件
├─────────────────────────────────────────┤
│  L3  事件日志:系统/应用/WMI/Defender    │ ← 还原时间线
├─────────────────────────────────────────┤
│  L4  对症日志:DPC 延迟 / WMI / 特定服务 │ ← 精准命中
└─────────────────────────────────────────┘

关键原则:每一层都必须有正面证据或反面证据才能进下一层,不许靠”我觉得”。这次就是在 L0/L1 跑偏了(UU 远程的虚拟输入驱动看着太像嫌疑犯了),幸亏 L3 的日志不撒谎。

4. 一步步怎么定位的(心路历程)

4.1 第一次跑偏:网易 UU 远程的 gvinput 驱动

最初看设备管理器时,发现了一组非常可疑的设备:

HIDClass  gvinput Device              netease   ROOT\HIDCLASS\0000
Mouse     HID-compliant mouse         netease   HID\GVINPUT&COL01...
Keyboard  HID Keyboard Device         Microsoft HID\GVINPUT&COL03...

网易装的虚拟 HID 驱动,同时创建了虚拟鼠标和虚拟键盘,能往系统输入队列注入事件。这玩意太符合”光标打架”的症状了——虚拟鼠标和物理鼠标抢着发事件,光标当然打架。

我一度写了一篇小作文把 UU 远程钉死了。但用户一句话点醒了我:“我装着但没用它,它总不能无缘无故启动服务夺舍我吧?”

——这话非常合理。一个不在用的串流软件,凭什么注入输入?**直觉必须有证据支持。**于是我翻了 GameViewer 的日志目录:

结果:自 2026/6/18 安装以来,零日志写入。txt\ 目录里只有 6/18 安装时的默认配置 JSON。也就是说 UU 远程从安装那天起就没活动过一次。嫌疑洗清。

这次跑偏的教训:“能做”和”正在做”是两回事。驱动有能力注入输入,不代表它真的注入了。日志是唯一的裁判。

4.2 系统日志干净的诡异

转去查 System 日志时,得到了一个反直觉的结果:System 日志异常干净。

5 小时窗口里只有十来条事件,全是 Hyper-V VmSwitch(WSL 网络用的)和 BTHUSB(蓝牙)。没有 GPU TDR(4101)、没有服务崩溃(7031/7034)、没有磁盘错误(7/11/51)、没有 Kernel-Power 异常。

这意味着:事故不是驱动级、硬件级、内核级的,而是用户态问题。范围一下子缩小了一半。

4.3 WMI 5858 风暴浮出水面

真正的突破口在 Microsoft-Windows-WMI-Activity/Operational 这个日志:

输出:

Name     Count
----     -----
07-04    1099

单日 1099 次 WMI 查询失败。按小时拆:

Name(小时)  Count
----------  -----
18          528
19          571

完全覆盖事故时段。看具体错误内容:

ClientProcessId = 36284
操作 = Start IWbemServices::ExecQuery -
        ROOT\StandardCimv2 :
        SELECT * FROM MSFT_NetAdapterStatisticsSettingData WHERE Name = 'WLAN'
ResultCode = 0x80041032

0x80041032 = WMI Provider 加载/执行失败。某个进程在反复查 WLAN 网卡的统计数据,每次都失败,失败后立刻重试——一个紧凑的死循环。

4.4 拆穿 svchost 的马甲:是 DoSvc

ClientProcessId = 36284 是个 svchost.exe,Windows 用 svchost 把一堆服务塞进同一个进程,光看进程名分不出真凶。拆解办法:

结果:

Name        : DoSvc
DisplayName : Delivery Optimization
State       : Running
StartName   : NT Authority\NetworkService
PathName    : C:\WINDOWS\System32\svchost.exe -k NetworkService -p

DoSvc 就是 Windows 的”传递优化”服务(Delivery Optimization)。它是 Windows 10/11 里负责 P2P 分发 Windows Update 和 Microsoft Store 应用更新的组件,为了优化 P2P 传输,会周期性轮询网卡吞吐量——这次轮询的是 WLAN 适配器的 MSFT_NetAdapterStatisticsSettingData。

但 WMI 网络适配器 provider 在某种条件下会持续返回 0x80041032(常见于网络适配器状态切换、Hyper-V vSwitch 抢占、或 provider 自身 bug)。DoSvc 的重试逻辑没有指数退避,没有上限,失败就立刻重试,于是陷入死循环。

4.5 为什么症状这么诡异?——三个症状的解释

锁定了根因,还要解释清症状,否则不算闭环。

症状解释
光标和鼠标打架实际上是 dwm(桌面窗口管理器)被饿死丢帧。光标由 dwm 渲染,当 svchost 抢占 CPU + Memory Compression 进程占 1.2GB 压缩内存时,dwm 帧率不稳,光标视觉上跳跃/瞬移,看起来像”和鼠标对抗”。不是真的有第二个输入源抢
键盘输入迟钝svchost 周期性占用 CPU + WMI 队列阻塞,输入事件被排队
前台程序仍正常运行DoSvc 跑在 NetworkService 账户,通过 svchost 间接影响系统,不直接杀用户进程
Taskmgr 自己挂了任务管理器枚举进程也走 WMI,WMI 一卡它跟着卡

一句话:这是用户态 WMI 风暴 + 高内存基线共同把 dwm 推过临界点,导致的”输入子系统饥饿”。和木马、和 UU 远程、和我 coding 的 Wails 程序,通通无关。

5. 神助攻清单(根因之外加重因素)

光有 DoSvc 一个嫌疑犯通常不会让机器瘫成这样。这次是多重压力凑齐了才爆的:

SRE 视角看:这是典型的多因素叠加触发的”雪崩阈值”。任何单个因素都不致命,但凑齐了就把系统推过崩溃点。根因(DoSvc)是触发器,其它是 fuel。

6.2 根治(防止复发)

打开 设置 → Windows Update → 高级选项 → 传递优化,把**“允许从其他电脑下载”**关掉。这样 DoSvc 就不会做 P2P 上传,也就不会去轮询 WLAN 统计。

8. 几条血泪教训

  1. 直觉必须有证据背书。UU 远程的 gvinput 驱动看起来是完美嫌疑犯,但日志告诉我它从没活动过。在没有日志证据之前,所有”我觉得”都只是假设。

  2. System 日志干净本身就是信息。它直接排除了驱动/硬件/内核事故,把搜索范围缩到用户态。学会从”什么都没发生”里读出”哪些事一定没发生”。

  3. svchost 不是单点信息。Windows 把几十个服务塞进 svchost,光看进程名毫无意义。Get-CimInstance Win32_Service | Where ProcessId -eq <PID> 才能扒掉它的马甲。

  4. Taskmgr 自己挂掉是硬证据。任务管理器走 WMI 枚举进程,WMI 一卡它跟着卡。这反过来证明 WMI 子系统确实出了问题,不是主观感觉。

  5. 应用层症状不一定有应用层根因。“光标打架”看起来像输入驱动问题,实际是 dwm 渲染丢帧;渲染丢帧看起来像 GPU 问题,实际是 CPU 被用户态服务抢占。症状在哪一层,根因不一定在哪一层。永远顺着日志走,不要顺着症状走。

  6. 多因素雪崩是 SRE 的常态。单看 DoSvc 一个 WMI 死循环其实不算大事,但叠加上 WSL 5.8GB、searchindexer 44%、Tai 9.85MB/s,就把 dwm 推过了临界点。复盘时既要找触发器,也要列清单 fuel。

  7. 最像木马的往往不是木马。这次 Defender 全阴、IoC 全无、网络全合法。中文用户的”银狐焦虑”是真实的,但绝大多数神秘卡顿都是 Windows 自己的 bug,先排除自家后院再怀疑外敌。
